</div></section></section><section aria-label="Article content"><section class="body main-article-body"><section class="abstract" id="abstract1"><h2>Abstract</h2>
<p>Across a host of MS-driven-omics fields, researchers witness the acquisition of ever increasing amounts of high throughput MS data and face the need for their compact yet efficiently accessible storage. Addressing the need for an open data exchange format, the Proteomics Standards Initiative and the Seattle Proteome Center at the Institute for Systems Biology independently developed the <em>mzData</em> and <em>mzXML</em> formats, respectively. In a subsequent joint effort, they defined an ontology and associated controlled vocabulary that specifies the contents of MS data files, implemented as the newer <em>mzML</em> format. All three formats are based on XML and are thus not particularly efficient in either storage space requirements or read/write speed. This contribution introduces <em>mz5</em>, a complete reimplementation of the <em>mzML</em> ontology that is based on the efficient, industrial strength storage backend HDF5. Compared with the current <em>mzML</em> standard, this strategy yields an average file size reduction to ∼54% and increases linear read and write speeds ∼3–4-fold. The format is implemented as part of the <em>ProteoWizard</em> project and is available under a permissive Apache license. Additional information and download links are available from <a href="http://software.steenlab.org/mz5" class="usa-link usa-link--external" data-ga-action="click_feat_suppl" target="_blank" rel="noopener noreferrer">http://software.steenlab.org/mz5</a>.</p></section><hr class="headless">
<p>MS data are acquired on a wide variety of mass analyzer technologies and brands that deliver data sets in various proprietary data formats and make use of a multitude of architecture-dependent libraries. In the past, this situation has severely complicated the development and application of alternative, vendor-independent data analysis pipelines (<a href="#B1" class="usa-link" aria-describedby="B1">1</a>–<a href="#B3" class="usa-link" aria-describedby="B3">3</a>), highlighting the need for and fueling the development of a common and open storage format for MS data sets (<a href="#B4" class="usa-link" aria-describedby="B4">4</a>, <a href="#B5" class="usa-link" aria-describedby="B5">5</a>).</p>
<p>The Proteomics Standards Initiative and the Seattle Proteome Center at the Institute for Systems Biology independently developed the <em>mzData</em> and <em>mzXML</em> formats, respectively (<a href="#B4" class="usa-link" aria-describedby="B4">4</a>, <a href="#B6" class="usa-link" aria-describedby="B6">6</a>). They subsequently merged their efforts, leading to the development of <em>mzML</em> (<a href="#B7" class="usa-link" aria-describedby="B7">7</a>), which features a generic ontology for the representation of MS data. The <em>mzML</em> format is universally applicable, and combined with the readily available open source reference implementation <em>ProteoWizard</em> (<a href="#B1" class="usa-link" aria-describedby="B1">1</a>), it significantly simplifies data import and export as well as general data handling. Most notably, <em>mzML</em> introduces a controlled vocabulary that enables the addition of novel as well as user-defined data types without requiring changes to the underlying XML schema. As a consequence, laboratories are able to store, analyze, and share MS data using an open exchange format, even for highly specialized workflows (<a href="#B8" class="usa-link" aria-describedby="B8">8</a>–<a href="#B11" class="usa-link" aria-describedby="B11">11</a>).</p>
<p>Continuous improvements in mass resolution and acquisition speed pose a serious challenge for existing data formats: current MS setups commonly acquire several hundreds of megabytes of data for each run, and space requirements for complete proteomics experiments easily exceed tens of gigabytes. As a consequence, the space and time efficiency of data format implementations have become increasingly critical.</p>
<p>Although based on excellent ontologies, relying on the extended markup language (XML)<a href="#G1" class="usa-link"><sup>1</sup></a> for the straightforward implementation of <em>mzData</em>, <em>mzXML</em>, and <em>mzML</em> makes for a major efficiency bottleneck. XML was designed to be a human readable, textual data format with considerable inherent verbosity and redundancy. XML was not designed for efficient bulk data storage, and the general modus operandi requires reading complete files to construct the XML parse tree. The <em>mzXML</em> and <em>mzML</em> formats partly circumvent these limitations by using base-64 encoding and (optional) compression of the raw MS scan data in combination with an application-specific indexing system. Despite the improvements gained from these efforts, vendor formats in general outperform <em>mzXML</em> and <em>mzML</em> in terms of space requirements, as well as in read and write efficiency.</p>
<p>This contribution introduces <em>mz5</em>, a novel data representation that combines the merits of the <em>mzML</em> ontology with the efficiency of the Hierarchical Data Format (HDF5) (<a href="#B12" class="usa-link" aria-describedby="B12">12</a>). HDF5 is an established industrial standard for efficient storage and retrieval of large amounts of complex data and is based on a portable binary representation. HDF5 was specifically designed for large data sets; the key features used in our <em>mz5</em> implementation are its native support for compression and cached partial read and write access. HDF5 library implementations are available for a range of languages and computational platforms, and the format is distributed under a permissive licensing scheme. Introduced more than 20 years ago, the continued use of HDF5 as the standard format for the NASA earth observing system, as well as its adaption as a prime format for data intensive applications in fields as diverse as astronomy, geology, remote sensing, and avionics (<a href="#B13" class="usa-link" aria-describedby="B13">13</a>–<a href="#B16" class="usa-link" aria-describedby="B16">16</a>), ensures broad, ongoing use and technical support for many years to come.</p>
<p>Our analyses show that <em>mz5</em> dramatically outperforms the XML-based representations of the <em>mzXML</em> and <em>mzML</em> formats in terms of both space requirements and Input/Output (I/O) speed and is competitive with proprietary vendor formats in terms of space requirements (<a href="#F1" class="usa-link">Fig. 1</a>). Because <em>mz5</em> is implemented inside the <em>ProteoWizard</em> (<a href="#B1" class="usa-link" aria-describedby="B1">1</a>) framework, it is already available for use by the mass spectrometry community, and <em>mz5</em> files can immediately be created from all open or proprietary formats supported by <em>ProteoWizard</em> (<a href="#F2" class="usa-link">Fig. 2</a>).</p>

<p>Twenty LC-MS/MS runs of fractionated HeLa S3 cell lysate were acquired in data-dependent acquisition mode on an LTQ/Orbitrap classic (Thermo Scientific) system hyphenated to a nanoflow HPLC system (Eksigent). The survey scan range was limited to <em>m/z</em> 400–2000 at a nominal resolution of 60,000, and MS/MS scans were limited to the eight most abundant precursor ions. The resulting raw data files were converted to <em>mzML</em> using the <em>ProteoWizard</em> (<a href="#B1" class="usa-link" aria-describedby="B1">1</a>) tool set, <em>mzML</em> files were converted to <em>mz5</em>, and the identity of the <em>mzML</em> and <em>mz5</em> file contents was confirmed. For all formats, the data were stored in compressed double precision. For the <em>mzXML</em> and <em>mzML</em> formats, indexing was turned on. All of the experiments were conducted using the same hardware, with all resources dedicated to the test runs (no parallel jobs). Overall, we consider the selected data set to be a reasonably common example of LC-MS/MS data acquisition and hence expect that the results generalize to a large majority of practical use cases.</p>
<p>To assess <em>mz5</em> performance, we conducted three types of comparative experiments, testing (i) write performance; (ii) read performance; and (iii) space requirements. For each of the 20 input files, we generated a set of 10 subsets of increasing sizes (sets of 800, 1600, up to 8000 spectra, and the complete set of all spectra present in the respective input file). This strategy yielded 220 test cases. All of the time measurements were averaged over 10 repeats for every test case, after discarding the minimum and maximum timings. For performance comparisons between different formats, we fitted linear models with intercepts and determined relative slopes over time and space (see <a href="http://www.mcponline.org/cgi/content/full/O111.011379/DC1" class="usa-link usa-link--external" data-ga-action="click_feat_suppl" target="_blank" rel="noopener noreferrer">supplemental materials</a>). <em>mz5</em> files were used to generate each test case for <em>mzXML</em>, <em>mzML</em>, and <em>mz5</em>, to guarantee that all three file formats contain the same data.</p>
<p>To test linear read performance, we measure the time it takes to read each of the test cases from the file it is stored in. <a href="#F1" class="usa-link">Fig. 1</a><em>a</em> shows the linear read times of all test cases <em>versus</em> the number of (<em>m/z</em>, abundance) pairs. The <em>mz5</em> format outperforms the <em>mzXML</em> and <em>mzML</em> formats by factors of ∼2.3 and ∼3.7, respectively. We note in passing that the <em>mz5</em> gains over <em>mzML</em> are not strictly linear; this indicates optimization opportunities for the parsing of smaller <em>mzML</em> files. Interestingly, the <em>mz5</em> linear read times also exhibit smaller variation compared with <em>mzXML</em> and, in particular, <em>mzML</em> read times.</p>
<p>For strictly random reading, <em>mz5</em> is significantly faster than <em>mzML</em> but performs slightly slower than <em>mzXML</em>. This is due to the underlying HDF5 caching/compression tradeoff. We focused on the vast majority of conceivable use cases and geared the tradeoff toward efficient linear reading. The random read and initialization performance tests, as well as benchmarks for different mass analyzer types, can be found in the <a href="http://www.mcponline.org/cgi/content/full/O111.011379/DC1" class="usa-link usa-link--external" data-ga-action="click_feat_suppl" target="_blank" rel="noopener noreferrer">supplemental materials</a>.</p>
<p>To test write performance, we extracted every test case from the respective <em>mz5</em> input file and measured the time it takes to write the data to disk, using <em>mzXML</em>, <em>mzML</em>, and <em>mz5</em>. Consequently, potential read time delays only cause a constant offset that is identical between the different formats and does not affect the slopes. <a href="http://www.mcponline.org/cgi/content/full/O111.011379/DC1" class="usa-link usa-link--external" data-ga-action="click_feat_suppl" target="_blank" rel="noopener noreferrer">supplemental Fig. 1<em>a</em></a> illustrates the results for all 220 test cases. Time measurements for <em>mzXML</em>, <em>mzML</em>, and <em>mz5</em> are shown as <em>diamonds</em>, <em>triangles</em>, and <em>circles</em>, respectively. It is apparent that <em>mz5</em> is consistently faster than <em>mzXML</em> and <em>mzML</em>. The read time-corrected relative slopes show improvements of a factor of ∼4.7 for <em>mz5</em> over <em>mzXML</em> and ∼3.9 over <em>mzML</em> (<a href="#TI" class="usa-link">Table I</a>).</p>

The <em>mz5</em> format compares very favorably against the Thermo and Bruker formats and is the best open alternative for the ABSciex format. The Bruker yep file data was generated from <em>Escherichia coli</em> whole cell lysate and was acquired on a Bruker amaZon instrument. The ABSciex wiff file data stems from subcellular fractions of a HeLa cell lysate and was analyzed by LC/MS on an TripleTOF 5600.</p>

<section id="sec3"><h4 class="pmc_sec_title"></h4>
<section id="sec4"><h5 class="pmc_sec_title">Implementation</h5>
<p>The <em>mz5</em> format maps the <em>mzML</em> ontology, as implemented in the <em>ProteoWizard</em> library, into a collection of HDF5 objects. The HDF5 library provides HDF5 object persistence.</p>
<p>The design of <em>mz5</em> is tailored to meet two specific goals: to create an open exchange format with both I/O speed and storage space requirements that rival existing vendor formats. The practical challenge was to develop data representations that enable the use of the HDF5 properties conducive to the above goals. In <em>mz5</em>, we represent <em>mzML</em> tags as HDF5 compound data types, which correspond to classical abstract data types. Collections of compounds are stored in instances of a multidimensional array type (H5::data set). Instances are compressed and stored to disk. It should be noted that the straightforward representation of <em>mzML</em> tags in terms of HDF5 groups is not a viable solution, because such an approach would prohibit data compression for technical reasons.</p>
<p>The HDF5 library is already highly optimized for file I/O (<a href="#B17" class="usa-link" aria-describedby="B17">17</a>). The <em>mz5</em> implementation guarantees optimized buffer sizes to minimize the number of necessary I/O operations, collecting raw data before bulk writes are performed. HDF5 natively supports compression filters, and to optimize compression rates, our implementation makes heavy use of HDF5 data types that are amenable to compression, in particular avoiding variable length data types where possible. In addition, <em>mz5</em> removes zero intensity scans and encodes <em>m/z</em> measurements in a delta mass representation, storing distances between consecutive <em>m/z</em> observations. The latter two measures yield a storage requirement reduction of 55%. Tests showed that there were no numerical errors introduced by delta storage.</p>
<p>The implementation at hand features considerable versatility: it is possible to adapt the data type of raw data (float/double), configure compression level and filtering strategies, and configure HDF5 buffer sizes. The default configuration provides a reasonable parameter setting for most common use cases. <em>mz5</em> is currently limited to collections of (<em>m/z</em>, abundance) and (time, abundance) for spectral and chromatographic measurements, respectively. The extension to other forms of measurements is possible and straightforward.</p></section><section id="sec5"><h5 class="pmc_sec_title">Application</h5>
<p>For practical applications, the main impact of the <em>mz5</em> format is likely going to be the significant decrease in storage space requirements. Many proteomics core facilities have substantial data storage and archiving costs, and the efficient use of available space can help to reduce these costs. Although standard database searches as they are currently performed are unlikely to benefit from increased read and write speeds, we expect that <em>mz5</em> will be of particular interest for spectral library searches, which are likely to become more relevant in the future (<a href="#B18" class="usa-link" aria-describedby="B18">18</a>, <a href="#B19" class="usa-link" aria-describedby="B19">19</a>). Furthermore, <em>mz5</em> will be of interest for data processing pipeline setups because the read and write speeds and storage space requirements offered by <em>mz5</em> will increase the efficiency of data exchange between different components of a tool chain and reduce the impact caused by data conversion from proprietary vendor formats to an open standard.</p>
<p>To enable the transparent, straightforward use of the <em>mz5</em> format in existing and future software applications, we have implemented <em>mz5</em> within the <em>ProteoWizard</em> library; hence, any application that already makes use of <em>ProteoWizard</em>-based transparent data file access will automatically support <em>mz5</em>. This eliminates the need for any <em>mz5</em>-specific conversion tools or software adaptions because the <em>ProteoWizard</em> interface already enables the use of many proprietary and open formats and requires only a single implementation effort on the user side. We have successfully used the <em>mz5/ProteoWizard</em> combination under Windows, Linux, and Mac OSX.</p></section><section id="sec6"><h5 class="pmc_sec_title">Summary</h5>
<p>This contribution introduces an efficient open data format for bulk mass spectrometry storage termed <em>mz5</em>. It combines the merits of HDF5, an established industry standard, and the <em>mzML</em> ontology developed by the HUPO Proteomics Standards Initiative. The <em>mz5</em> format offers dramatically faster I/O than the <em>mzXML</em> and <em>mzML</em> formats and requires only approximately half (54%) the storage space. The current <em>mz5</em> implementation is fully integrated into the <em>ProteoWizard</em> library and supports conversion operations for all proprietary data formats supported by <em>ProteoWizard</em> itself. All software is available from: <a href="http://software.steenlab.org/mz5" class="usa-link usa-link--external" data-ga-action="click_feat_suppl" target="_blank" rel="noopener noreferrer">http://software.steenlab.org/mz5</a>.</p>
<p>The <em>mz5</em> format is a first step toward providing extended capabilities for MS data storage. Depending on future <em>mzML</em> ontology development and forthcoming HDF functionality, this may include physical and logical merging of large experimental data sets, distributed read and write access for high throughput workflows, and novel strategies for large data repositories (<a href="#B20" class="usa-link" aria-describedby="B20">20</a>, <a href="#B21" class="usa-link" aria-describedby="B21">21</a>).</p></section></section></section></section><section id="ack1" class="ack"><h2 class="pmc_sec_title">Acknowledgments</h2>
