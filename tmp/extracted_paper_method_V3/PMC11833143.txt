</div></section></section><section aria-label="Article content"><section class="body main-article-body"><section class="abstract" id="abstract1"><h2>ABSTRACT</h2>
<section id="rcm9990-sec-0001"><h3 class="pmc_sec_title">Rationale</h3>
<p>The field of mass spectrometry imaging is currently devoid of standardized protocols or commercially available products designed for system suitability testing of MSI platforms. Machine learning is an approach that can quickly and effectively identify complex patterns in data and use them to make informed classifications, but there is a technical barrier to implementing these algorithms. Here we package the machine learning algorithms into a user‐friendly interface to make community‐wide implementation of this protocol possible.</p></section><section id="rcm9990-sec-0002"><h3 class="pmc_sec_title">Methods</h3>
<p>The software package is built entirely in the Python language using the PySimpleGUI library for the construction of the interface, Pandas and Numpy libraries for data formatting and manipulation, and the Scikit‐Learn library for the implementation of machine learning algorithms. Training data is collected on an instrument under clean and compromised conditions that can then be used to evaluate model performance and to train models prior to interrogating unknown samples before, during, or after experiments.</p></section><section id="rcm9990-sec-0003"><h3 class="pmc_sec_title">Results</h3>
<p>Detailed instructions are provided for the effective use of the SLICE‐MSI software package to use machine learning to evaluate instrument condition of MSI platforms. File formatting and generalizable steps are clearly described to make the implementation of this package easy for multiple labs and different MSI platform configurations.</p></section><section id="rcm9990-sec-0004"><h3 class="pmc_sec_title">Conclusions</h3>
<p>In this protocol, we demonstrate SLICE‐MSI, a machine learning graphical user interface for efficient and easy implementation of QC instrument classification of mass spectrometry imaging platforms.</p></section><section id="kwd-group1" class="kwd-group"><p><strong>Keywords:</strong> graphical user interface, machine learning, mass spectrometry imaging, quality control, system suitability testing</p></section></section><section id="rcm9990-sec-0005"><h2 class="pmc_sec_title">1. Introduction</h2>
<p>Quality control (QC) and system suitability testing (SST) are important steps in mass spectrometry (MS) workflows to ensure accurate data and reproducibility of methods across platforms. These protocols are commonly employed in traditional MS methods, but there are currently no standardized protocols or commercially available kits for SST of mass spectrometry imaging (MSI) platforms. Having a mix and a set of analytes to monitor is a good start, but that collected data has to be analyzed and interpreted to make a determination about the instrument condition. Machine learning (ML) algorithms can handle large amounts of data and effectively make sense of it through powerful pattern recognition, which makes it a great option for SST. To make this protocol more easily implemented into many laboratories and workflows, we needed to remove the technical barrier of developing and implementing ML algorithms. To this effort, we developed a graphical user interface (GUI) that is intuitive and easy to use that can take QC data and apply ML algorithms to determine the working state of the instrument and MSI platform. This novel interface lacks the comprehensiveness of other packages, but this is intentional and adds to the ease of usability and intuitiveness that is needed for this application and that is currently absent in the field. In this work, we detail the file format necessary and breakdown using the software step‐by‐step to obtain model performance metrics on the training data and obtain instrument conditions before, during, or after experiments.</p></section><section id="rcm9990-sec-0006"><h2 class="pmc_sec_title">2. Protocol</h2>
<p>
<strong>Supervised Learning for Instrument Classification and Evaluation for Mass Spectrometry Imaging (SLICE‐MSI)</strong> is freeware shared by North Carolina State University (available at <a href="https://doi.org/10.5061/dryad.msbcc2g7c" class="usa-link usa-link--external" data-ga-action="click_feat_suppl" target="_blank" rel="noopener noreferrer">https://doi.org/10.5061/dryad.msbcc2g7c</a>) intended for use, but not exclusively, with Cambridge Isotope Laboratories, Inc.’s <strong>Mass Spectrometry Imaging Quality Control Kit v1.0 (MSI QC Kit v1.0)</strong>. The purpose of this executable is to utilize training data to characterize an MSI platform by ML algorithms and then test the suitability of the instrument at any point in an analysis. The steps described guide the user to (1) extract data from the desired software, (2) format the data features for processing, and (3) walk through the GUI to describe the available data analysis options. This pipeline is not required for the analysis of QC data from the <strong>MSI QC Kit v1.0</strong> but serves as a compatible option for interrogation of an array of imaging platforms and may be used to evaluate the results from cross‐platform applications.</p>
<section id="rcm9990-sec-0007"><h3 class="pmc_sec_title">2.1. Instruction for Use</h3>
<p>The procedure to follow contains step‐by‐step instructions for a data analysis strategy of QC and SST data from the <strong>MSI QC Kit v1.0</strong>. This protocol was developed as a suggested, but optional, approach for characterizing the suitability of a user's specific platform with the ML algorithm of choice, along with the ability to classify the instrument's state before, during, or after sample analysis.</p>
<p>
<strong>IMPORTANT NOTE: Applying this executable requires the collection of “clean” and “compromised” datasets to train ML models and characterize these states on your instrument platform. Explicit details are described in previous work</strong> [<a href="#rcm9990-bib-0001" class="usa-link" aria-describedby="rcm9990-bib-0001">1</a>], <strong>and the required prerequisites are as follows:</strong>
</p>
<ol id="rcm9990-list-0001" class="list" style="list-style-type:decimal">
<li id="rcm9990-li-0001"><p>Collecting regions of interest (ROIs) on your instrument in a “clean” state</p></li>
<li id="rcm9990-li-0002"><p>Collecting ROIs on the same instrument in a “compromised” state</p></li>
<li id="rcm9990-li-0003"><p>Collecting ROI(s) before, during, and/or after analysis to classify the instrument as “clean” or “compromised”</p></li>
<li id="rcm9990-li-0004"><p>The ability to extract data metrics, or features, from the RAW or converted datasets (e.g., imzML)</p></li>
<li id="rcm9990-li-0005"><p>The ability to organize data into spreadsheets and save .csv data files</p></li>
</ol>
<p>It is recommended that more than 50 ROIs (i.e., datasets) [<a href="#rcm9990-bib-0001" class="usa-link" aria-describedby="rcm9990-bib-0001">1</a>] be collected on both a platform under clean and compromised conditions, where it is ideal to collect an equal number of datasets for each condition containing a sufficient number of scans. For instance, the original method development for establishing this protocol collected 120 “clean” and 120 “compromised” ROIs with 400 scans in each.</p>
<p>The steps enclosed consider the data from this original work [<a href="#rcm9990-bib-0001" class="usa-link" aria-describedby="rcm9990-bib-0001">1</a>], and each observation is the average of specific features within the dataset [<a href="#rcm9990-bib-0002" class="usa-link" aria-describedby="rcm9990-bib-0002">2</a>]. The procedure herein may be adapted to the users' desire; however, the strategy discussed is based on successful implementation and classification of the IR‐MALDESI MSI platform.</p>
<section class="bt xbox font-sm" id="rcm9990-blkfxd-0001"><p class="img-box line-height-none margin-x-neg-2 tablet:margin-x-0 text-center"><img class="graphic" src="https://cdn.ncbi.nlm.nih.gov/pmc/blobs/4be6/11833143/ae340307aba6/RCM-39-e9990-g012.jpg" loading="lazy" id="jats-graphic-1" height="177" width="331" alt="2.1."></p></section><ul id="rcm9990-list-0002" class="list" style="list-style-type:none"><li id="rcm9990-li-0006">
<span class="label">A.</span><div class="display-inline p">Data file preparation for ML analysis
<ol id="rcm9990-list-0003" class="list" style="list-style-type:decimal">
<li id="rcm9990-li-0007"><div class="p">From the software interface of your choosing, extract the relevant data metrics, or features, that will be used for modeling. The features used in the pilot study were the monoisotopic and isotope abundance, monoisotopic and isotope mass measurement accuracy (MMA), monoisotopic and isotope detection frequency (DF), monoisotopic and isotope relative standard deviation (RSD) in the abundance, and the spectral counts. Each of these features was extracted/calculated for each of the mix components (caffeine, sulfamethazine, L‐thyroxine, and multiple PEG peaks). These features should represent the ROI and will need to be extracted for both the “clean” and “compromised” conditions. These datasets will eventually be organized into the same data file.</div></li>
<li id="rcm9990-li-0008"><div class="p">Create a new, blank, spreadsheet for data organization and handling. This can be in any spreadsheet/data handling software if the file can be saved or exported to a *.csv file for use with SLICE‐MSI.</div></li>
<li id="rcm9990-li-0009"><div class="p">In this new spreadsheet, the top row should consist of data feature names (e.g., MMA, DF), and each following row will be an individual replicate or observation. The leftmost column will be named “Condition”. The rest of the columns will be named specific to each analyte in the analysis (e.g., caffeine) with the appropriate data feature (e.g., MMA).</div></li>
<li id="rcm9990-li-0010"><div class="p">Organize the extracted data in the spreadsheet such that each column is a unique data feature (e.g., MMA) and each row is a unique replicate, or ROI. The instrument state during data collection (i.e., “Clean” or “Compromised”) should be specified in the first column of the row that contains its corresponding data. An example of this formatting is shown in Figure <a href="#rcm9990-fig-0001" class="usa-link">1</a>. The labels “Clean” and “Compromised” need to be used for the SLICE‐MSI program to work properly.</div></li>
<li id="rcm9990-li-0011"><div class="p">Once all observations or ROIs have been incorporated, save this file as a *.csv file. This data file will serve as your training dataset during instrument condition evaluation and will be referred to as such from this point on. This file will be used to train the ML models on what data looks like from a clean or compromised platform.</div></li>
<li id="rcm9990-li-0012"><div class="p">For any ROI(s) you wish to test from an unknown instrument condition, follow Steps A1–A5 again for this new, unknown observation and maintain the same order for all the feature headers (i.e., Row 1) as the training dataset. However, since the condition of the instrument will be determined after modeling, the “Condition” column will be omitted completely. If multiple ROIs are to be evaluated, they can all be included in a single file. Once you have saved this data as a *.csv file, this will serve as your testing data for an unknown instrument condition and will be referenced as your unknown dataset moving forward.</div></li>
</ol>
</div>
</li></ul>

<strong>(OPTIONAL)</strong> Select the box to the left of “Run negative control samples” to include this in the modeling and/or the box to the left of “Run 10‐Fold Cross Validation”.
<ol id="rcm9990-list-0008" class="list" style="list-style-type:lower-alpha">
<li id="rcm9990-li-0019"><div class="p">Negative controls are used to check against confounding variables and ensure that the identified model performance comes from true learning by the models. The class labels (“clean” and “compromised”) are randomized 10 times to generate 10 distinct “random” datasets evaluated by the models. This means that the models should not be able to identify patterns in the data and should act as random predictors (accuracy of 50%) unless data leakage or confounding variables are present.</div></li>
<li id="rcm9990-li-0020"><div class="p">A tenfold cross‐validation randomly creates 10 subgroups of the dataset, and each subgroup is used as a testing set. This captures a model wholistic view of the model's performance since each observation is, at some point, included in the testing set.</div></li>
</ol>
</div>
</li>

<li id="rcm9990-li-0022">
<span class="label">7.</span><div class="display-inline p">After approximately 30 s, an output window will open (Figure <a href="#rcm9990-fig-0004" class="usa-link">4</a>) and show the model's
<ol id="rcm9990-list-0009" class="list" style="list-style-type:lower-alpha">
<li id="rcm9990-li-0023"><div class="p">accuracy—percent of correctly classified instances from the testing dataset from the 70:30 train:test split.</div></li>
<li id="rcm9990-li-0024"><div class="p">cross‐validation accuracy—total accuracy achieved when each of the observations were used as part of the testing set.</div></li>
<li id="rcm9990-li-0025"><div class="p">confusion matrix—matrix representation of the predictions and true classes. The top left and bottom right corners are correctly classified, while the top right and bottom left corners are incorrectly classified. This can be important to note to identify bias in the models one way or the other.</div></li>
<li id="rcm9990-li-0026"><div class="p">Kappa statistic—evaluation metric that considers chance agreement, more robust metric when dealing with unbalanced datasets.</div></li>
<li id="rcm9990-li-0027"><div class="p">AUROC—Area under the receiver operating characteristic curve, which is a metric that provides information on the ability of the models to distinguish separate classes.</div></li>
</ol>
</div>
</li>
